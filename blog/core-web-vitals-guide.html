Core Web Vitals 가이드, LCP·INP·CLS 기준과 홈페이지 개선 방법

2026. 10. 28 · 이수연

PageSpeed Insights에서 점수는 높은데 서치 콘솔의 "핵심 성능 보고서"에는 경고가 뜨는 경우가 있습니다. 반대로 점수는 낮은데 보고서는 양호하다고 나오기도 합니다. 이 차이를 이해하려면 Core Web Vitals(코어 웹 바이탈)가 무엇을 어떻게 재는지부터 알아야 합니다.

로딩 속도 전반의 개선은 이미 홈페이지 로딩 속도 개선 가이드에서 다뤘습니다. 이 글은 그 연장선에서 구글이 공식 지표로 삼는 세 가지 항목의 기준과 해석, 개선 순서에 집중합니다.

1. Core Web Vitals란

Core Web Vitals는 구글이 사용자 경험의 핵심 요소를 로딩, 상호작용, 시각적 안정성 세 측면에서 수치화한 지표 모음입니다. 구글 검색의 페이지 경험 평가에 참고되는 신호 중 하나이지만, 검색 순위를 좌우하는 유일한 요소는 아닙니다. 검색 의도에 맞는 좋은 콘텐츠가 여전히 가장 중요하며, 비슷한 품질의 페이지끼리 경쟁할 때 경험이 차이를 만드는 요소로 이해하는 것이 정확합니다.

무엇보다 이 지표들은 실제 방문자가 느끼는 불편을 측정하기 때문에, 순위와 별개로 이탈률과 문의 전환에 직접 영향을 줍니다.

2. 세 가지 지표와 통과 기준

지표의미좋음개선 필요나쁨
LCP
(Largest Contentful Paint)		화면에서 가장 큰 콘텐츠(대표 이미지·제목 블록)가 보이기까지의 시간2.5초 이하2.5~4초4초 초과
INP
(Interaction to Next Paint)		클릭·탭·키 입력 후 화면이 반응하기까지의 지연200ms 이하200~500ms500ms 초과
CLS
(Cumulative Layout Shift)		로딩 중 화면 요소가 예기치 않게 움직인 정도0.1 이하0.1~0.250.25 초과

구글은 페이지 방문의 75번째 백분위수 값으로 기준 충족 여부를 판단하며, 모바일과 데스크톱을 따로 평가합니다. 즉 대부분의 방문자(4명 중 3명)가 좋은 경험을 해야 통과입니다. INP는 이전의 FID(최초 입력 지연)를 대체한 지표입니다.

3. 측정 도구와 필드·랩 데이터의 차이

측정 결과가 도구마다 다른 이유는 데이터의 출처가 다르기 때문입니다.

구분필드 데이터랩 데이터
출처실제 방문자 브라우저에서 수집(Chrome 사용자 경험 데이터)정해진 환경에서 시뮬레이션(Lighthouse)
대표 도구서치 콘솔 핵심 성능 보고서, PageSpeed Insights 상단의 "실제 사용자 경험"PageSpeed Insights 하단 진단, 크롬 개발자 도구 Lighthouse
강점실제 경험을 반영, 순위 신호와 직결즉시 측정 가능, 원인 진단에 유리
한계방문자가 적으면 데이터 없음, 반영에 시간 소요실제 기기·네트워크와 다를 수 있음

실무 순서는 이렇습니다. 서치 콘솔에서 문제가 있는 페이지 유형을 파악하고, PageSpeed Insights와 Lighthouse로 원인을 진단해 수정한 뒤, 몇 주 후 필드 데이터가 개선됐는지 확인합니다. 서치 콘솔 사용법은 구글 서치 콘솔 가이드를 참고하세요. 트래픽이 적은 사이트는 필드 데이터가 아예 없을 수 있는데, 그때는 랩 데이터를 기준으로 개선하면 됩니다.

4. LCP 개선 방법

LCP 요소는 대개 첫 화면의 대표 이미지나 큰 제목 블록입니다. PageSpeed Insights 진단에서 어떤 요소가 LCP인지 먼저 확인하세요.

  • 대표 이미지 경량화: 크기에 맞는 해상도와 WebP 등 효율적인 형식을 씁니다. 방법은 홈페이지 이미지 최적화 가이드를 참고하세요.
  • LCP 이미지에 지연 로딩 금지: 첫 화면 대표 이미지에 lazy loading을 걸면 오히려 늦어집니다. 스크롤 아래 이미지에만 적용합니다.
  • 우선순위 부여: 대표 이미지에 fetchpriority="high"를 주거나 preload를 고려합니다.
  • 서버 응답 시간 단축: 호스팅 성능, 캐시, CDN 활용이 효과적입니다 (호스팅·SSL·CDN 가이드).
  • 렌더링 차단 요소 줄이기: 첫 화면에 불필요한 CSS·스크립트·웹폰트를 줄입니다.

5. INP 개선 방법

INP가 나쁘다는 것은 버튼을 눌러도 화면이 곧바로 반응하지 않는다는 뜻입니다. 주로 자바스크립트가 메인 스레드를 오래 점유할 때 생깁니다.

  • 서드파티 스크립트 점검: 채팅 위젯, 여러 개의 분석·광고 태그, 팝업 도구는 INP의 흔한 원인입니다. 꼭 필요한 것만 남기세요.
  • 무거운 인터랙션 단순화: 과도한 스크롤 애니메이션, 복잡한 슬라이더, 대형 메뉴 애니메이션을 줄입니다.
  • 긴 작업 쪼개기: 개발 가능한 환경이라면 긴 자바스크립트 작업을 나누고, 필요한 시점까지 로드를 미룹니다.
  • 입력에 즉시 반응하는 UI: 폼 제출이나 메뉴 열기 같은 동작은 먼저 시각적 반응을 주고 무거운 처리는 뒤로 넘깁니다.

6. CLS 개선 방법

텍스트를 읽다가 이미지가 늦게 뜨면서 글이 아래로 밀린 경험이 있을 것입니다. 이것이 레이아웃 이동이고, 잘못된 버튼 클릭까지 부를 수 있습니다.

  • 이미지·영상에 크기 지정: width, height 속성이나 aspect-ratio로 공간을 미리 확보합니다.
  • 동적 요소 공간 예약: 배너, 쿠키 안내, 광고, 임베드가 들어갈 자리의 높이를 미리 잡아 둡니다.
  • 웹폰트 교체 이동 줄이기: font-display 설정과 비슷한 크기의 대체 폰트 지정이 도움이 됩니다 (홈페이지 폰트 가이드).
  • 상단 삽입 금지: 사용자 동작 없이 이미 보이는 콘텐츠 위에 새 요소를 끼워 넣지 않습니다.

7. 플랫폼별 현실적인 접근

아임웹, 카페24, 웹플랫폼 같은 호스팅형 빌더는 서버·코드 수정이 제한되어 이미지 최적화, 불필요한 위젯 제거, 팝업·애니메이션 절제 같은 사용자 단 개선이 중심이 됩니다. 반대로 자체 개발이나 CMS 환경은 캐시, 번들 최적화, 이미지 파이프라인까지 손볼 수 있습니다. 플랫폼 선택의 차이는 노코드 vs 전문가 비교에서 정리했습니다. 한 번 만든 뒤에도 콘텐츠와 스크립트가 쌓이면 지표가 나빠지므로 유지보수 체크리스트에 성능 점검을 포함하세요.

8. 개선 우선순위 정하기

  1. 서치 콘솔에서 "나쁨" URL 그룹 확인: 같은 템플릿을 쓰는 페이지는 한 번의 수정으로 묶여서 개선됩니다.
  2. 모바일 먼저: 방문자 다수가 모바일이고 평가 기준도 더 엄격하게 나오는 경우가 많습니다 (모바일 최적화 가이드).
  3. 가장 쉬운 것부터: 이미지 용량, 불필요 스크립트 제거, 이미지 크기 지정은 효과 대비 난이도가 낮습니다.
  4. 수정 후 재측정: 필드 데이터는 반영에 시간이 걸리므로 몇 주간 추이를 봅니다.

9. 자주 하는 실수

  • 점수 100점에 집착: 목표는 만점이 아니라 "좋음" 기준 통과와 실제 체감 개선입니다.
  • 메인 페이지 한 곳만 측정: 문의가 일어나는 서비스·상세 페이지를 함께 봐야 합니다.
  • 랩 점수만 보고 판단: 실제 방문자 환경이 반영된 필드 데이터를 같이 확인하세요.
  • 기능 추가 후 재측정 생략: 새 위젯 하나가 INP를 크게 해칠 수 있습니다.

10. 자주 묻는 질문

Core Web Vitals를 통과하면 검색 순위가 오르나요?

통과가 순위 상승을 보장하지는 않습니다. 구글이 참고하는 여러 신호 중 하나이며, 콘텐츠의 관련성과 품질이 우선입니다. 다만 느리거나 불안정한 페이지는 이탈과 전환 손실로 이어지므로, 순위와 별개로 개선할 가치가 큽니다.

서치 콘솔에 "데이터 부족"이라고 나옵니다. 어떻게 하나요?

필드 데이터는 일정 수준 이상의 방문이 있어야 수집됩니다. 방문이 적은 사이트는 데이터가 표시되지 않을 수 있으며, 이때는 PageSpeed Insights의 랩 데이터와 진단 항목을 기준으로 개선하면 됩니다.

FID는 이제 사용하지 않나요?

네, INP가 FID를 대체한 Core Web Vitals 지표입니다. FID가 첫 입력의 지연만 봤다면 INP는 방문 중 발생한 상호작용 전반의 반응성을 평가합니다.

모바일과 데스크톱 중 어느 쪽을 먼저 개선해야 하나요?

대부분의 사이트는 모바일 방문 비중이 높고 모바일 환경에서 지표가 더 나쁘게 나오므로 모바일을 먼저 개선하는 것이 일반적입니다. 서치 콘솔에서 두 환경의 보고서를 각각 확인해 우선순위를 정하세요.

정리하며

Core Web Vitals는 어려운 용어처럼 보이지만 결국 "빨리 보이고, 누르면 바로 반응하고, 읽는 중에 흔들리지 않는 페이지"를 만드는 세 가지 기준입니다. 서치 콘솔로 문제 페이지를 찾고, 이미지와 스크립트부터 정리한 뒤, 몇 주 후 데이터로 확인하는 순서로 시작해 보세요.
