다국어 홈페이지·hreflang

다국어 홈페이지 제작 가이드, hreflang과 URL 구조로 해외 검색까지 설계하기

2026. 11. 04 · 이수연

"영문 페이지도 만들어 주세요." 홈페이지 제작에서 흔히 나오는 요청입니다. 그런데 한국어 페이지를 번역해 하나 더 만드는 것만으로는 해외 검색에서 제대로 노출되지 않는 경우가 많습니다. 검색 엔진이 어떤 페이지가 어떤 언어·지역 사용자를 위한 것인지를 이해해야 하고, 사용자도 자기 언어의 페이지로 자연스럽게 안내받아야 하기 때문입니다.

의료 분야의 다국어 전략은 병원·성형외과 다국어 홈페이지 가이드에서, 제조업의 영문 페이지는 제조업·B2B 홈페이지 가이드에서 업종별로 다뤘습니다. 이 글은 업종과 상관없이 적용되는 다국어 구조 설계와 hreflang을 정리한 기술 가이드입니다.

1. 다국어 홈페이지가 정말 필요한가

다국어는 만들기보다 유지하기가 어렵습니다. 한국어 페이지를 수정할 때마다 다른 언어 페이지도 맞춰야 하기 때문입니다. 시작 전에 다음을 점검하세요.

  • 실제 타깃이 있는가: 외국인 환자, 해외 바이어, 외국인 관광객 등 구체적인 대상과 목표 시장이 있는지
  • 응대할 수 있는가: 해당 언어로 문의에 답하고 거래·예약을 처리할 인력과 체계가 있는지
  • 범위를 정했는가: 전체 사이트를 번역할지, 핵심 페이지(서비스·제품·문의)만 번역할지
  • 유지 계획이 있는가: 내용이 바뀔 때 번역을 갱신할 담당자와 절차가 있는지

처음에는 핵심 페이지만 영어로 정확하게 만들고 성과를 본 뒤 확장하는 방식을 권합니다. 어설픈 번역이 가득한 10개 언어보다 정확한 한 개 언어가 훨씬 낫습니다.

2. 언어 타깃과 지역 타깃

다국어 설계의 첫 결정은 언어만 구분할지, 언어와 지역을 함께 구분할지입니다.

구분hreflang 값 예시쓰는 경우
언어만en, ja, ko언어별로 내용이 같고 지역별 차이가 크지 않을 때 (대부분의 소규모 사이트)
언어 + 지역en-US, en-GB, zh-CN, zh-TW가격·통화·법적 안내·배송 조건이 지역마다 다를 때
기본값x-default어느 언어에도 맞지 않는 사용자를 위한 기본 페이지(언어 선택 페이지 또는 대표 언어 페이지)

언어 코드는 ISO 639-1(두 글자), 지역 코드는 ISO 3166-1 Alpha 2(두 글자 대문자)를 따릅니다. 지역 코드만 단독으로 쓸 수는 없고, 항상 언어 코드가 먼저 와야 합니다.

3. URL 구조 3가지 비교

방식예시장점단점
국가 도메인(ccTLD)example.kr, example.jp국가 타깃이 가장 분명함도메인 비용·관리 증가, 사이트별 신뢰를 따로 쌓아야 함
서브도메인en.example.com서버·플랫폼을 분리하기 쉬움설정과 분석이 복잡해질 수 있음
하위 디렉터리example.com/en/하나의 도메인에서 관리, 설정이 단순함서버 위치를 언어별로 나누기 어려움

소규모 사이트와 대부분의 중소기업은 하위 디렉터리 방식(/en/, /ja/)이 관리하기 가장 수월합니다. URL 설계 원칙은 URL 구조 가이드를 참고하세요. 쿠키나 JavaScript로 언어만 바꾸고 URL은 그대로인 방식은 언어별 페이지를 따로 인식하기 어려우므로 피해야 합니다. 언어마다 고유한 URL이 있어야 검색 엔진이 색인할 수 있습니다.

4. hreflang 작성 규칙과 예시

hreflang은 같은 내용의 언어·지역별 페이지가 서로 연결되어 있다는 것을 검색 엔진에 알려 주는 표기입니다. 구글 등 일부 검색 엔진이 활용하며, 사용자의 언어에 맞는 버전을 검색 결과에 보여 주는 데 도움을 줍니다.

HTML head에 쓰는 방법

한국어, 영어, 일본어 페이지가 있는 경우, 세 페이지 모두의 head에 다음과 같이 같은 목록을 넣습니다.

<link rel="alternate" hreflang="ko" href="https://example.com/ko/service/" />
<link rel="alternate" hreflang="en" href="https://example.com/en/service/" />
<link rel="alternate" hreflang="ja" href="https://example.com/ja/service/" />
<link rel="alternate" hreflang="x-default" href="https://example.com/en/service/" />

꼭 지켜야 할 규칙

  1. 상호 연결: A 페이지가 B를 가리키면 B도 A를 가리켜야 합니다. 한쪽만 있으면 무시될 수 있습니다.
  2. 자기 자신 포함: 각 페이지의 목록에는 자기 자신의 언어 버전도 들어가야 합니다.
  3. 절대 URL 사용: https://를 포함한 전체 주소로 적습니다.
  4. 정확한 코드: 존재하지 않는 코드(kr, jp 같은 잘못된 표기)를 쓰지 않습니다. 한국어는 ko, 일본어는 ja입니다.
  5. 페이지 단위로 연결: 사이트 전체가 아니라 같은 내용의 페이지끼리 연결합니다. 번역 버전이 없는 페이지는 목록에서 제외합니다.
  6. canonical과 충돌하지 않기: 각 언어 페이지의 canonical은 자기 자신을 가리켜야 합니다. 모든 언어 페이지의 canonical을 한국어 페이지로 지정하면 hreflang이 무력해집니다.
  7. 색인 가능한 페이지만: noindex이거나 다른 URL로 리다이렉트되는 페이지는 목록에 넣지 않습니다.

세 가지 구현 위치, 하나만 일관되게

hreflang은 HTML head, HTTP 응답 헤더(PDF 등 HTML이 아닌 파일), XML 사이트맵 중 한 곳에 쓸 수 있습니다. 페이지 수가 많다면 사이트맵 방식이 관리가 편하며, 여러 위치에 중복해 쓰면 서로 어긋날 위험이 있으므로 한 가지 방식으로 통일하세요. 사이트맵 작성은 XML Sitemap·robots.txt 가이드를 참고하세요.

5. 사용자 경험 설계

  • 언어 전환 링크는 눈에 띄게: 헤더 우측에 "KO / EN / JP"처럼 두고, 언어 이름은 해당 언어 자체로(한국어, English, 日本語) 표기합니다. 국기 아이콘은 언어와 국가가 일치하지 않으므로 피하세요.
  • 자동 리다이렉트 지양: IP나 브라우저 언어만 보고 강제로 이동시키면 검색 엔진과 사용자 모두 다른 언어 페이지에 접근하기 어려워집니다. 대신 상단에 "영어 페이지로 이동하시겠습니까?" 같은 안내 배너를 보여 주는 방식이 안전합니다.
  • 같은 내용의 페이지로 이동: 언어를 바꿀 때 메인으로 돌려보내지 말고 현재 보던 페이지의 번역본으로 연결하세요.
  • html lang 속성: 각 페이지의 <html lang="en">을 해당 언어로 지정합니다. 스크린리더와 번역 도구가 참고합니다 (웹접근성 가이드).
  • 로컬 형식: 날짜, 통화, 전화번호 국가 코드, 주소 형식을 해당 지역에 맞게 표기합니다.

6. 번역 품질과 콘텐츠 현지화

  • 직역이 아닌 현지화: 한국에서 통하는 표현이 해외에서는 어색합니다. 서비스 설명과 CTA는 해당 언어 사용자의 관점에서 다시 쓰세요 (카피라이팅 가이드).
  • 기계 번역은 검수 후 사용: 기계 번역 초안은 속도에 도움이 되지만, 사람이 검수하지 않은 대량 자동 번역은 품질 문제로 이어질 수 있고 신뢰를 해칩니다.
  • 용어집 만들기: 상호, 서비스명, 전문 용어의 표기를 통일해 모든 페이지에 같은 번역을 적용합니다.
  • 키워드도 언어별로 조사: 한국어 키워드를 번역한 단어가 해당 언어에서 실제로 검색되는 단어와 다를 수 있습니다. 언어별로 따로 조사하세요 (키워드 리서치 가이드).
  • 메타 정보·이미지 alt도 번역: 제목 태그, 메타 설명, alt 텍스트, 구조화 데이터 값까지 해당 언어로 맞춰야 검색 결과에 제대로 보입니다 (제목 태그·메타 설명 가이드).
  • 이미지 속 텍스트 주의: 이미지에 글자가 박혀 있으면 번역마다 이미지를 새로 제작해야 합니다. 가능하면 텍스트는 HTML로 두세요.

일본어·중국어 웹폰트는 파일 용량이 커서 속도에 영향을 줍니다. 언어별 폰트 설정과 서브셋은 홈페이지 폰트 가이드를, 해외 방문자 대상 속도 개선은 호스팅·SSL·CDN 가이드를 참고하세요.

7. 플랫폼별 접근

플랫폼마다 다국어 지원 방식과 hreflang 자동 생성 여부가 다릅니다. 도입 전에 반드시 확인하세요.

  • 호스팅형 빌더(아임웹 등): 다국어 사이트 기능을 제공하는 경우가 많지만, 언어별 URL 구조와 hreflang 출력 방식이 플랫폼 정책에 따라 다릅니다. 실제 발행된 페이지의 소스를 열어 확인하세요.
  • 쇼핑몰 플랫폼: 다국어·다통화는 플랫폼별로 지원 수준이 크게 다릅니다. 해외 판매 계획이 있다면 카페24 vs 쇼피파이 비교를 참고하세요.
  • CMS·자체 개발: 다국어 플러그인이나 라우팅 설정으로 hreflang을 자동 출력하도록 구성할 수 있습니다. 번역 관리 워크플로까지 함께 설계해야 합니다 (CMS 구조 가이드).

한국 검색 노출은 한국어 페이지 중심의 설정(네이버 서치어드바이저 등)으로 따로 관리해야 합니다 (서치어드바이저 가이드). 다국어 구조가 한국어 페이지의 색인과 URL에 영향을 주지 않는지 함께 점검하세요.

8. 검증과 모니터링

  1. 페이지 소스 확인: 발행된 페이지의 소스에서 hreflang 목록이 의도한 대로 출력되는지, 모든 버전이 서로를 가리키는지 직접 열어 봅니다.
  2. 서치 콘솔 URL 검사: 언어별 페이지가 색인되었는지, canonical이 자기 자신인지 확인합니다 (서치 콘솔 가이드).
  3. 사이트맵 제출: 언어별 URL이 모두 사이트맵에 포함되어 있는지 점검합니다.
  4. 언어별 유입 분석: 애널리틱스에서 언어·국가별 유입과 전환을 비교해 확장·축소를 결정합니다 (애널리틱스 가이드).
  5. 변경 시 동기화: 페이지를 삭제·이동하거나 URL을 바꿀 때는 hreflang과 리다이렉트를 함께 갱신합니다 (404·301 리다이렉트 가이드).

9. 자주 발생하는 hreflang 오류

오류원인해결
상호 링크 누락한 언어 페이지에만 hreflang 작성모든 버전에 같은 목록 적용
잘못된 언어·지역 코드kr, jp, en-UK 등ko, ja, en-GB로 수정
canonical 충돌모든 언어 페이지의 canonical이 한국어 페이지각 언어 페이지가 자기 자신을 canonical로 지정
리다이렉트·noindex URL 지정실제 색인되지 않는 주소를 목록에 포함최종 색인 URL만 사용
번역 없는 페이지 연결언어 버전이 없는데 hreflang 생성번역본이 있는 페이지만 연결
상대 경로 사용/en/service/처럼 도메인 생략전체 절대 URL로 작성

10. 자주 하는 실수

  • 번역만 하고 구조를 나중에 고민: URL과 hreflang 설계를 처음에 해야 나중에 뒤엎지 않습니다.
  • 언어는 많은데 유지가 안 됨: 갱신되지 않은 외국어 페이지는 오히려 신뢰를 떨어뜨립니다.
  • 자동 리다이렉트로 사용자를 강제 이동: 사용자와 검색 엔진 모두 접근이 어려워집니다.
  • 해외 문의 대응 체계 없이 페이지만 제작: 문의가 와도 답하지 못하면 의미가 없습니다.
  • 해외 법규·개인정보 기준 확인 생략: 대상 국가에 따라 개인정보 보호 등 법적 요구가 다를 수 있습니다 (개인정보처리방침 가이드).

11. 자주 묻는 질문

hreflang이 없으면 다국어 페이지가 검색되지 않나요?

검색되지 않는 것은 아니지만, 사용자 언어에 맞는 페이지 대신 다른 언어 버전이 노출될 수 있습니다. hreflang은 어떤 언어·지역에 어떤 페이지를 보여 줄지 검색 엔진이 판단하도록 돕는 신호이므로, 여러 언어 페이지가 있다면 설정하는 것이 좋습니다.

구글 번역 위젯만 붙여도 다국어 홈페이지가 되나요?

번역 위젯은 방문자가 브라우저에서 임시로 번역해 보는 방식이어서 언어별 고유 URL이 없고, 검색 엔진이 번역된 내용을 색인하지 못합니다. 해외 검색 노출이 목표라면 언어별로 별도 URL과 검수된 번역 페이지가 필요합니다.

영어 페이지만 만들 때도 hreflang이 필요한가요?

한국어와 영어 두 버전이 같은 내용으로 존재한다면 hreflang을 설정하는 것이 좋습니다. 상호 연결과 자기 참조, x-default까지 갖추면 검색 엔진이 두 페이지의 관계를 정확히 이해합니다.

URL 구조는 하위 디렉터리와 서브도메인 중 무엇이 좋은가요?

소규모 사이트는 하나의 도메인에서 관리하기 쉬운 하위 디렉터리 방식(/en/)을 가장 많이 권합니다. 언어별로 서버나 플랫폼을 분리해야 하거나 대규모 운영 조직이 있다면 서브도메인이나 국가 도메인을 검토할 수 있습니다.

정리하며

다국어 홈페이지는 번역본을 하나 더 만드는 일이 아니라 언어별 고유 URL, hreflang, 현지화된 콘텐츠, 유지 체계를 함께 설계하는 일입니다. 타깃과 범위를 좁혀 핵심 페이지부터 정확하게 시작하고, 구조는 하위 디렉터리처럼 단순하게 가져가세요. 그리고 발행 후에는 소스와 서치 콘솔로 hreflang이 의도대로 작동하는지 확인하는 것을 잊지 마세요.

해외 고객에게도 찾아지는 홈페이지,
다국어 구조부터 함께 설계해 드립니다
